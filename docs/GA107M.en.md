# GA107M RTX 3050 Ti Laptop port — workflow and evidence

**English only.** This fork adapts the exact-card unlock transaction to an
HP RTX 3050 Ti Laptop GPU (GA107M) on Windows. The upstream RTX 3090 FE
case remains separate (its docs and evidence are preserved unchanged);
this document describes the laptop port only. Nothing here adds support
for any other board.

## Target card (single documented machine)

| Item | Value |
|---|---|
| GPU | NVIDIA GeForce RTX 3050 Ti Laptop GPU, 4 GiB, 20 SM |
| PCI identity | `10de:25a0`, subsystem `103c:88e5`, BDF `0000:01:00.0` |
| VBIOS | `94.07.3a.00.6e` |
| Chip / memory register (cold, decode on) | `0xb77000a1` / `0x1000` |
| Cold GFW PLM / BOOT / CPUCTL | `0x8b8f` / `0x3ff` / `0x10` (identical to the 3090 profile) |
| Cold FEAT PLM / WPR2_HI | `0xffffff8f` / `0x0` |
| Entry selectors | **vary per cold boot** (e.g. `0x53520035`/`5`, `0x13720035`/`7`); latched at runtime, never pinned |
| iGPU display | Intel Iris Xe `8086:9a49` / `103c:88e5` at `0000:00:02.0` |
| Driver | 617.14 (unchanged by any phase) |

The GA107 firmware path is the GA102 one in the vendored core: the pinned
610.43.03 HAL selects the GA102 Booter/GSP binaries for GA107, and
[IHaBiS02/ga107-unlock](https://github.com/IHaBiS02/ga107-unlock) verified
the same transaction on an LG RTX 3050 (Linux). The laptop-specific FWSEC
DMEM round-up fix from that port is included here
(`gpu_unlock_fwsec_dmem_transfer`).

## Measured result (this machine, 2026-10-25)

Two full transactions executed cleanly from UEFI (RUN03/RUN04 reports:
FWSEC halt `scratch=0`, V67 staged, `SS0=0x88888888` verified pre- and
post-FLR, clean handoff, `transaction result=0 clean=1`). With the dGPU
held out of runtime D3cold at logon:

| 8192³ GEMM, ops/SM/clk (clock-normalized) | Locked | Unlocked |
|---|---:|---:|
| FP16 in / FP32 acc | 502-513 | **987** |
| BF16 in / FP32 acc | 504-507 | **962** |
| TF32 in / FP32 acc | 250-252 | unchanged (SS1 preserved by default) |
| FP32 pedantic | 163-170 | unchanged |

FP16 GEMM: 16.7 TFLOPS @ 1657 MHz / ~59 W locked → 25.8 TFLOPS @
1305 MHz / ~48.5 W unlocked. ~55% more throughput at ~20% less power.
TF32 doubling requires the explicit `entryLatchedSs1Full` opt-in and is
unverified on this card.

**Persistence:** the override survives the driver bind but is erased by
runtime D3cold, because the card's fuse-based init re-programs the
selectors at every power-on (entry-SS0 entropy proves this). Hold the GPU
awake (below) to keep it. Full analysis with source-dive receipts:
[GA107M-PERSISTENCE.en.md](GA107M-PERSISTENCE.en.md).

## Workflow

### 0. Prerequisites

FAT32 USB stick, Secure Boot disabled (suspend BitLocker first if used),
pinned [firmware assets](ASSETS.en.md) generated but **not** on the
preflight/probe stick (assets are only needed for the experimental build).

### 1. Preflight (read-only)

Build `GA107M-PREFLIGHT.EFI` (`unlock/build-wsl.sh`, or `build.ps1` with
LLVM). Stage on the stick:

```
\EFI\BOOT\BOOTX64.EFI            (the preflight app)
\GA107M-PREFLIGHT\               (empty; captures land here)
```

Boot it (F9 → USB), boot Windows, take
`GA107M-PREFLIGHT\RUNnn\REPORT.TXT`. On this firmware the card boots with
PCI decode disabled (`command=0x0000`), so register/PROM reads return
erased-flash values — expected; the report records config, BAR0 and GOP
classification. **This build performs no GPU writes of any kind.**

### 2. Decode probe (one config write)

Build `GA107M-PROBE.EFI` (`build-wsl.sh --probe`). It performs exactly
one write — the PCI MEM decode-enable the Windows driver performs on
every boot, with fail-closed readback (MEM set, BME stays clear, DEVCNTL
frozen; DEVSTS deltas are hardware status and are logged, not treated as
drift) — then records the real cold registers, PROM hash + dump, and the
FWSEC descriptor. Captures land in `\GA107M-PROBE\RUNnn\`.

### 3. Transcribe the profile

```
python tools/ga107m-parse-preflight.py GA107M-PROBE\RUNnn\REPORT.TXT
```

Review the sanity findings (FWSEC `engine_mask=0x400`, DMEM geometry
`ret=0`, zero NVIDIA GOPs, 16 MiB BAR0, memory register `0x1000`) and
transcribe the emitted pins into `unlock/port.h` (PROM SHA-256, chip,
GFW/PLM values, BAR0 base; then set `GU_PROFILE_READY 1`). The
experimental build **fails closed with `#error`** until this is done, so
nobody can build a write-capable EFI for a card whose profile was not
captured from that very card's probe report.

### 4. Validate before hardware

Run the cross-host suite (`unlock/run-cross-tests.sh` from WSL to build,
then `run-cross-tests.ps1` on Windows to execute), optionally with
`-PromFixture <your PROM.BIN> -AssetsDir <pinned assets>`: the
full-transaction mock then executes FWSEC → V67 → selectors → FLR in
simulation against **your** PROM capture and the pinned assets.

### 5. Experimental manual unlock

Build `GA107M-EXPERIMENTAL-entryLatchedSs1Preserve.EFI`
(`build-wsl.sh --experimental entryLatchedSs1Preserve`; the SS1=0x8 TF32
experiment is the explicit `entryLatchedSs1Full` variant). Stage on the
stick:

```
\EFI\BOOT\BOOTX64.EFI            (the experimental app)
\GA107M-UNLOCK\ASSETS\           (the five pinned .bin files)
\GA107M-UNLOCK\                   (empty; the run report lands here)
```

Full shutdown (not Fast Startup), F9 → USB. The app re-verifies every gate
against live hardware, loads and hash-verifies the assets, then waits:
**press `U` once to run the transaction; Esc or 30 s cancels.** It returns
to the boot menu; choose Windows and let it boot normally.

### 6. Hold and measure

At logon, start the hold before the driver parks the dGPU:

```
python tools\hold_gpu_windowed.py        (keep the window open)
tools\setup-hold-startup.ps1            (optional: Startup shortcut, no admin)
```

Measure with `python tools\bench_gemm.py` — clock-normalized
ops/SM/clk, which classifies 512 vs 1024 directly and is immune to
power-limit clock differences. Closing the hold window releases the GPU;
a park erases the override; rerun the unlock boot to restore it.

## Safety properties retained from upstream

Fail-closed gates (identity, config, BAR0, PROM hash, cold-state pins,
entry-latch), one-shot manual confirmation, DMA/FLR containment,
BME containment, STOP/POWER OFF halt on unsafe return, USB-only media,
Secure Boot required off, no VBIOS flashing, no eFuse writes, no driver
replacement. The laptop display stays on the Intel iGOP throughout; the
unlock target must expose no GOP of its own (console-wrapper GOPs that
exactly mirror the physical Intel GOP are classified as mirrors).

## Limits

One laptop, one VBIOS, evidence first. No stability testing beyond the
two documented transactions and same-session benchmarks; no sleep/hibernate
resume validation; no repeated-automatic-boot reliability data. The hold
trades battery for persistence (the dGPU cannot power down while held),
and the pre-logon window is not covered. LLM inference on small models is
memory-bandwidth-bound and will not show the unlock; compute-bound work
(GEMM, large-batch tensor work) does.
